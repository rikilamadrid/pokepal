# Printing resolver + recognition client with fixture transport

## Status

In Progress

## Parent Feature

`19-card-recognition.md`

## Blocked by

- `18.1` — contract types and catalog adapter

## Goal

Given what a vision model read off a card, PokéPal resolves it to an exact printing, a ranked shortlist, or unmatched — through one client API that Batch Scan and Trade Check both call, runnable today against recorded responses.

## Context

- Read: `02-target-architecture.md` §Recognition pipeline, contract rules; `src/lib/catalog/`

## Changes

- `src/lib/recognition/resolve.ts`: pure resolver (number + official count first, then name; scoring on name similarity, HP, regulation mark, language); tiers per contract; never fabricates a printing.
- `src/lib/recognition/index.ts`: `recognize(image, { mode })` → `ScanBatch`, with a `RecognitionTransport` interface; `fixtureTransport` (tests/dev only) and an `edgeTransport` stub for 19.2.
- Client image prep: resize to ~1600px (batch) / ~1024px (trade-check), JPEG, in memory only.

## Verification

- `npm test`: exact; ambiguous (same number, different sets); unmatched; secret rare (number > official count); promo codes; Japanese card; wrong-name/right-number conflict lowers tier.
- No image bytes appear in the returned `ScanBatch` (test).

## Out of Scope

- Edge Function and model calls (19.2). UI.

## Notes / Decisions

- Scoring and tiers are documented at the top of `src/lib/recognition/resolve.ts`.
  `exact` needs a unique candidate with the same printed number, an agreeing name
  (similarity >= 0.8), the same set denominator when one was read, and no read
  HP or regulation mark that contradicts it. A read without a name is never
  `exact`.
- Repair (Tester findings at a52e32b), decisions taken on the side that cannot
  produce an unsupported `exact`:
  - Similar names at one number/denominator ("Charizard" vs "Charizard ex"): a
    read HP or regulation mark that disagrees removes a candidate's identity,
    which separates such pairs on a full read. An exact-name match alone does
    not break the tie (a dropped suffix is a plausible misread), so a read
    without HP/regulation stays `ambiguous`. The contradiction rule also applies
    to a lone candidate: a conflicting HP or regulation mark demotes it to
    `ambiguous`.
  - Language not read: lookup still defaults to English, but the tier is capped
    at `ambiguous` (the identity candidate still ranks first). An unread
    language cannot prove a language-qualified printing id.
  - `recognize()` wraps any non-`RecognitionError` transport rejection in a
    `RecognitionError` (original kept as `cause`). Open question for the human
    (19.2 / review UI): should one card's catalog lookup failure fail the whole
    batch (current behavior) or degrade only that card to `unmatched`?
  - Response guard: besides `data:` URIs, `recognize()` refuses strings with
    JPEG/PNG/GIF/WebP base64 openings or any unbroken base64 run of 120+
    characters; `setCodeHint` and match reasons are capped at 200 characters;
    a printing `imageUrl` must be https.
- Name similarity ignores a trailing catalog qualifier in parentheses (TCGdex
  names `swsh1-178` "Professor's Research (Professor Magnolia)").
- Transports return resolved cards plus server timings (`RecognitionResponse`);
  `recognize()` validates them with Zod, refuses inline image data (see above), and
  builds the `ScanBatch` with every candidate `pending` and nothing chosen.
- The fixture transport replays recorded model extractions through the resolver;
  the recorded data lives under `test/fixtures/`, not in `src/`.
